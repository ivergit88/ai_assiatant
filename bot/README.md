# MAX bot (Python 3.12) — transport layer для голосового ассистента

**Зона ответственности B / папка `bot/`** согласно командному плану. Бот **не** извлекает даты, не пишет напрямую в PostgreSQL и не вызывает MCP. Только MAX → ASR → Agent API → MAX. Анализ текста, контекст уточнений и работа с задачами принадлежат сервису `agent/` (C).

## Что работает в этом каркасе

- Текст MAX → `POST /v1/agent/message` → текстовый ответ.
- Голос MAX (`audio`, а также аудиофайл) → (готовая транскрипция MAX, если есть; иначе скачивание вложения и ASR) → текст → тот же Agent API → ответ.
- ASR заменяется настройкой: `whisper` (реальное распознавание речи локально), `http` (адаптер под совместимый HTTP ASR), `disabled` (только если сам MAX передал готовую транскрипцию). Байты аудио **не перекодируются**.
- Redis FSM `idle → recognizing → thinking → idle` с TTL 5 минут и защитой от одновременных запросов одного пользователя; после рестарта `bot:state:*` сбрасываются.
- «Голос получил, распознаю…», «Распознал: … Думаю…», ответ; дружелюбные сообщения об ошибках; игнорирование сообщений ботов, дублей и групповых чатов.
- Отдельный мок-агент, который соблюдает согласованный контракт, **не сохраняет данные**.

> **Не проверено на реальном MAX в этом окружении:** для этого нужен `MAX_TOKEN` и живой доступ к API; проект содержит автотесты на искусственных обновлениях. Развернутый публичный бот/прототип не создан этим архивом.

## Как получить MAX_TOKEN

При наличии верифицированного профиля MAX для партнёров: раздел **Чат-боты → Создать**, заполнить карточку и дождаться модерации; затем **Чат-боты → ⋮ → Настройки → скопировать токен**. Официальная инструкция: https://dev.max.ru/docs/chatbots/bots-create/create . Если коллега уже зарегистрировал бота, попросите у него **доступ через защищённый канал**, не публикуйте токен в GitHub. Если в MAX бот не создаётся из-за ограничений аккаунта, локальные тесты и мок-агент всё равно можно разрабатывать без токена.

## Быстрый запуск в Docker Compose

Требуются Docker, Docker Compose, токен бота из кабинета MAX. **Важно:** официально создание бота требует верифицированного профиля российской организации, ИП или самозанятого и прохождения модерации (по документации до 48 рабочих часов); согласуйте выдачу токена с командой заранее.

```bash
cp .env.example .env
# В .env заполнить MAX_TOKEN действительным токеном
# ASR_PROVIDER=whisper, WHISPER_MODEL=base установлены по умолчанию

docker compose -f compose.bot.yaml up --build
```

`mock-agent` слушает `http://localhost:8001`, `redis` — `localhost:6379`, `bot` опрашивает API MAX. Отправьте своему боту текст или голосовое. **Первое голосовое** с локальным Whisper скачает модель; для этого нужен интернет и достаточно памяти. Если нет доступа к модели, используйте готовый HTTP ASR. Вопросы про задачи пока получат ответ «Мок-агент получил… Ничего не сохранено» — это ожидаемо.

Для остановки `docker compose -f compose.bot.yaml down`.

## Локальный запуск без Docker (Python 3.12, uv)

```bash
uv sync --extra asr --extra dev
cp .env.example .env
# Заполнить MAX_TOKEN, запустить Redis на localhost:6379
# .env автоматически не загружается: экспортируйте переменные:
set -a; source .env; set +a

uv run uvicorn bot.mock_agent:app --host 127.0.0.1 --port 8001
# в другом терминале с теми же переменными:
uv run python -m bot
```

Вместо `uv` можно использовать `python -m pip install -e '.[asr,dev]'` в виртуальном окружении. Для внешнего агента поменяйте `AGENT_URL` на адрес реального `agent/` (например `http://agent:8001` внутри Docker-сети), мок отключите.

## Agent API: строго по командному контракту

Бот отправляет:

```http
POST /v1/agent/message
Content-Type: application/json

{"user_id":"123456789","text":"Напомни завтра позвонить Ивану"}
```

Ожидает:

```json
{"reply_text":"Уточни время напоминания", "status":"need_clarification", "events":[]}
```

`status` может быть `done`, `need_clarification`, `error`. Для бота даже `need_clarification` — обычный текстовый ответ: контекст уточнений живёт на стороне агента (Redis `agent:ctx:<id>`), не в FSM бота. `bot:state:<id>` содержит временную фазу и ID запроса, а не контекст диалога.

## ASR и голосовые

1. `MAX` отправляет update `message_created` с вложением `type=audio`, `payload.url` (иногда в аудио доступен `payload.transcription`). Если транскрипция есть, она переиспользуется.
2. Бот загружает URL аудио с MAX CDN, ограничивая загрузку 15 МБ и проверяя HTTPS+домен.
3. `ASR_PROVIDER=whisper` — `faster-whisper` с русским языком и CPU `int8`, модель `base`. Не требует платного API; требует загрузки весов и времени CPU. Форматы OGG/Opus/MP3 декодируются внутри PyAV.
4. `ASR_PROVIDER=http` — `POST ASR_HTTP_URL` как multipart `file`, ожидаемый JSON `{"text":"..."}`. При `ASR_HTTP_TOKEN` добавляется `Authorization: Bearer ...`. **Коммерческие платформы имеют собственные контракты**: при выборе конкретного ASR исследователем реализуйте соответствующий адаптер в `bot/asr.py`.

## FSM

```text
idle (нет ключа в Redis)
    │ пришёл текст            │ пришёл голос
    ▼                        ▼
 thinking                 recognizing
    │                        │ ASR вернул текст
    │                        ▼
    │                     thinking
    └─────────────┬──────────┘
                  │ success/error/finally
                  ▼
                 idle
```

Redis `SET NX EX` защищает от повторной обработки сообщения до окончания текущего запроса. `bot:state:{user_id} = "thinking:<request_id>"` или `"recognizing:<request_id>"`, TTL 300 секунд; переход и освобождение выполняются атомарно. Если пользователь отправит ещё одно сообщение до завершения, бот скажет «Ещё думаю над прошлым запросом». TTL предотвращает вечную блокировку. При старте очищаются **только** ключи `bot:state:*` (не `agent:ctx:*`). Сброс безопасен в предположении одного экземпляра бота.

## Тесты и стиль

```bash
uv run --extra dev pytest -q
uv run --extra dev ruff check bot tests
uv run --extra dev ruff format --check bot tests
```

Тесты проверяют текстовый и голосовой маршрут, использование транскрипции MAX, занятость пользователя, состояние после ошибок, отдельные сессии, дубликаты, группы, форму запросов к MAX и URL аудио. Тесты используют фейки; реальный сценарий проверяется отдельно с токеном в MAX.

## Особенности MAX API

- Используется `https://platform-api2.max.ru` и **сырой токен** в `Authorization` (не `Bearer`). По документации MAX для HTTPS может понадобиться добавить сертификат Минцифры в доверенные сертификаты вашей системы/контейнера; не отключайте TLS-проверку.
- Для прототипа `GET /updates` — Long Polling с `marker`; нельзя одновременно иметь активную webhook-подписку. В продакшене MAX требует Webhook; переключение транспорта событий — отдельная задача перед деплоем.
- `POST /messages?chat_id=...` (если в диалоге `chat_id` отсутствует — `?user_id=...`) с телом `{"text": "..."}`. Вложения с аудио скачиваются по `payload.url`.
- На отправке соблюдается ограничение ~2 сообщения/сек в один диалог; для ответа можно использовать `user_id`, если `chat_id` в update равен `null`.
- По соображениям приватности личный ассистент обслуживает только чаты типа `dialog`.

Официальная документация: https://dev.max.ru/docs-api/methods/GET/updates/ ; https://dev.max.ru/docs-api/methods/POST/messages ; https://dev.max.ru/docs-api/objects/Update/

## Как встроить в командный монорепозиторий

Перенесите `bot/` в корень монорепы, объедините `pyproject.toml`/`compose.bot.yaml` с инфраструктурой А. Владельцу контрактов А покажите `bot/models.py` для синхронизации с `common/` — **не правьте самостоятельно чужую папку**. У сервиса есть свой Dockerfile `bot/Dockerfile`. В командной сети направьте `AGENT_URL` на реальный агент. Исследователь E выберет ASR и передаст параметры адаптера. В продакшен передайте управление событиями на webhook.
